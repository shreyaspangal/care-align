## D-001 — Application framework: Next.js 16 (App Router)

| Option | For | Against |
|---|---|---|
| **Next.js 16** | RSC + server actions fit our DAL/injection patterns; `after()` enables the non-blocking AI step; chassis + enforcement stack already built on it; Vercel deploy is zero-config | Framework churn risk; RSC mental-model complexity |
| Remix / React Router 7 | Simpler mental model, great forms | No `after()` equivalent as clean; whole chassis re-derived |
| Vite SPA + Hono API | Maximum control, smallest magic | Two codebases to secure/deploy; loses RSC data-locality; auth/session plumbing manual |
| Expo (React Native) | True mobile app — capture is mobile-first | Blocks web entirely; app-store friction contradicts ship-fast; PWA-grade web covers V1 capture |

**Choice:** Next.js 16. **Why:** the deciding factor is not fashion — it's that the 593-line enforcement stack, Supabase SSR wiring, and team knowledge already target it, and `after()` + server actions map 1:1 onto the capture pipeline. **Revisit:** if dogfooding shows mobile-web capture friction that only a native app fixes (trigger: founder stops using it because of the browser).

## D-002 — Backend: Supabase (Postgres + Auth + RLS)

| Option | For | Against |
|---|---|---|
| **Supabase** | Postgres + auth + RLS in one; FTS/trgm/pgvector native; hard-won two-layer discipline documented; local dev + migrations tooling | RLS complexity (mitigated: single `family_id` policy shape); vendor coupling (mitigated: it's plain Postgres underneath) |

**Choice:** Supabase. **Why:** the product is a relational timeline with one clean tenancy rule — exactly what Postgres+RLS is for, and we carry scar tissue (GRANT+RLS, silent-0-row) that de-risks it. **Revisit:** sustained RLS performance issues at real scale.

## D-003 — File storage: **Supabase Storage — RESOLVED 2026-07-16 by spike**

| Option | For | Against |
|---|---|---|
| **Supabase Storage (chosen)** | Same vendor/billing/auth context; bucket colocated with the DB (Singapore); signed upload + signed read both proven; image transformations work on our plan | Slightly less turnkey client-upload DX than Blob |
| Vercel Blob (v1 inheritance) | Presigned pattern proven in v1 | A second vendor; measured 8x slower from India; private-blob reads need extra auth plumbing |
| Cloudflare R2 | Cheapest at scale, zero egress | Third vendor + manual presign plumbing; scale doesn't warrant it |

**Spike results (2026-07-16, founder's machine in India, 300KB payload, private `documents` bucket):** Supabase — signed-upload token 125ms, direct PUT 404ms (status 200), signed-read URL 79ms, read 384ms, **transform signed URL worked (200)**. Vercel Blob — upload 3,195ms, raw private URL read 403. Client-upload token flow = `createSignedUploadUrl` (server) + direct `PUT` (client) — bytes never transit our server.

**Consequences:** `@vercel/blob` and `BLOB_READ_WRITE_TOKEN` removed; capture pipeline uploads to the private `documents` bucket; the document-file route serves auth-checked signed URLs; thumbnails can use built-in transforms. **Revisit trigger:** egress costs at real scale.

**Gap found in Phase 2 (2026-09-06):** the bucket was created via the dashboard during the spike, never via migration — it shipped with zero RLS policies (default-deny) and blocked every upload until caught during capture testing. Fixed with `supabase/migrations/20260906000000_storage_documents_rls.sql` + a same-day correction for a column-shadowing bug (`docs/ANTI_PATTERNS.md` #11, #12). Any future bucket must get its policies written as a migration in the same phase it's introduced, not left to be discovered later.

## D-004 — Document-understanding model: Claude via AI SDK v6 — **eval-decided, provisional**

| Option | For | Against |
|---|---|---|
| **Claude (Haiku tier dev / Sonnet-class prod)** | Strong vision + instruction-following for the explain-never-advise constraint; team knows its failure modes; AI SDK abstracts swap | Cost vs alternatives unproven for OUR documents |
| Gemini Flash | Cheap, strong OCR reputation | Constraint-following on the advisory boundary unproven |
| GPT-4.1/5-mini class | Comparable | Same — unproven on our docs |
| Direct Anthropic SDK (no AI SDK) | One less abstraction | Loses cheap provider swap + structured-output ergonomics; v1 patterns all AI-SDK-shaped |

**Choice:** Claude via AI SDK as the starting point; **the Phase 2 eval set is the judge** — if another model scores equal-or-better on field accuracy AND boundary compliance at lower cost, we swap (the AI SDK makes that a one-line model-map change). **Revisit:** every eval run.

**Free-model research (2026-09-06, prompted by an Anthropic billing outage mid-Phase-2 testing):** researched whether a free OpenRouter/NVIDIA/Ollama model could stand in for Claude. Findings, so this isn't re-litigated from scratch next time:

- Every free, vision-capable, tool-calling-capable model checked on OpenRouter (NVIDIA Nemotron Nano 12B VL, MiniMax M3) **documents that it does not enforce the response schema** — the exact precondition for the v1 Phase-12 failure (a field silently drops from an otherwise valid-shaped object, no error, only caught later by a downstream Zod mismatch or, worse, not caught at all since a missing nullable field is indistinguishable from a genuinely absent one).
- NVIDIA's flagship Nemotron models are **text-only** — not viable for this vision task at all; only two NVIDIA models are both free and vision-capable, and neither enforces schema.
- Google's Gemini isn't actually free via OpenRouter (needs a paid balance); Google AI Studio's own free tier **trains on submitted prompts/responses** by default — a data-governance concern for medical documents, separate from the model-quality question.
- Ollama (self-hosted): only `qwen3-vl` combines vision + tool-calling in one model; everything else in the Ollama vision lineup (`llava`, `qwen2.5vl`, `llama3.2-vision`, etc.) doesn't accept tool calls at all. Self-hosting also trades a per-token bill for owning a GPU box's uptime — a different risk shape, not a cheaper version of the same risk.
- Confirmed by reading `node_modules` source directly: `@ai-sdk/anthropic` is the reason Claude is safe here — it computes whether native structured output is available and, if not, **forces an internal tool call** to get schema-shaped JSON; there is no unenforced path on that provider. The `ai` core itself just forwards the schema request to whichever provider is configured — for a provider that doesn't enforce it, the SDK has no way to detect the degradation (`result.warnings` stays empty; OpenRouter exposes no per-model capability flag to check this programmatically either).

**Decision:** `AI_MODEL_TIER=development` now points at a free OpenRouter model (`nvidia/nemotron-nano-12b-v2-vl:free`, `lib/ai/models.ts`) for cost reasons while building out the rest of Phase 2 — **accepted as a known, bounded risk for local dev only.** `AI_MODEL_TIER=production` stays Anthropic, unchanged. A provider-independent safety net was added regardless (`lib/ai/organize.ts`: logs `result.warnings`, hard `OrganizeSchema.safeParse` boundary before any DB write) — it cannot catch the "silently missing field" class of failure described above, only outright malformed output, so it does not substitute for using an enforcing provider.

**Revisit trigger (hard gate, not a suggestion):** the dev-tier free model must be swapped back to Anthropic (or another schema-enforcing provider, e.g. OpenAI's `json_schema` mode) before: (a) the Phase 2 eval set is run for real scoring, (b) any pre-launch/production testing, (c) any dogfooding with real family documents. A dev-tier default is a cost workaround, never evidence that a model is safe for this constraint.

**Wider model sweep, including DeepSeek (2026-09-08, prompted by the MVP cost-ceiling goal, D-018):** re-checked the entire field against the same hard bar (vision + PDF support, and schema enforcement that is either impossible to violate or detectable when violated — not just "usually follows the schema"), reading provider source and primary docs directly rather than summaries.

- **DeepSeek is a hard no, and not primarily on the schema question.** Its own privacy policy states outright that the service is "not designed or intended to process sensitive Personal Data (e.g. ... health ...)" and instructs users not to send it — disqualifying on its own for a medical-records product. Also stores data in the PRC, has no no-training commitment in its Terms of Service, has **no PDF support** (only JPEG/PNG/GIF/WebP — `lib/ai/organize.ts` passes PDFs straight through), and downscales images to ~800×800 (too lossy for fine print on a lab report). Separately, its official `@ai-sdk/deepseek` provider does not actually enable DeepSeek's own beta strict-mode tool-calling by default — the SDK's default path sends an unenforced `json_object` request, the same silent-degradation class this decision already ruled out for OpenRouter's free models. Even the hand-built strict-mode workaround wouldn't survive contact with `OrganizeSchema`: DeepSeek's strict mode has no `null` type and no `date` string format, both of which this schema uses throughout (Rule 2's `.nullable()` fields).
- **OpenAI's structured-output guarantee is real and stronger than this entry's original table assumed.** Verified in `@ai-sdk/openai` source: `strictJsonSchema` defaults to `true`, and OpenAI's own documentation states the model "will always generate responses that adhere to your supplied JSON Schema" — the only escape hatches (a `refusal` field, or truncation at the token limit) are both detectable, not silent. `gpt-5-nano` ($0.05/$0.40 per MTok) and `gpt-5-mini` ($0.25/$2.00) are both vision- and PDF-capable and pass this bar.
- **Anthropic's own enforcement is also better-documented now than this entry originally recorded** — a native `json_schema` structured-output path exists (not just the tool-forcing fallback originally described), read directly from `node_modules/@ai-sdk/anthropic`.
- **No free option clears the bar.** Every free vision-capable model on OpenRouter (10 checked, including the current dev-tier default) either has no way to force a tool call or is explicitly documented by OpenRouter itself as "not guaranteed" schema compliance ("treat it as a strong hint"); Gemini's free tier trains on submitted data; Groq's constrained-decoding models are all text-only.

**Decision (supersedes this entry's original dev-tier choice):** `AI_MODEL_TIER=development` moves to OpenAI `gpt-5-nano` — genuinely enforced, vision+PDF capable, and at realistic MVP volume (~100 documents/month) costs **$0.15/month**, i.e. the free model was never actually saving anything measurable while carrying the exact silent-failure risk this decision exists to avoid. `AI_MODEL_TIER=production` stays a live open question between Anthropic (Sonnet $4.20/mo or Haiku $2.10/mo at the same volume, D-018) and `gpt-5-mini` ($0.75/mo, same enforcement guarantee) — put `gpt-5-mini` on the eval slate alongside the current Anthropic tier per this entry's original "eval set is the judge" rule; take whichever wins on field accuracy and boundary compliance, with cost as the tiebreaker. **Implemented 2026-09-08:** `lib/ai/models.ts` development tier now points at `gpt-5-nano` via `@ai-sdk/openai`; the now-unused `@openrouter/ai-sdk-provider` dependency was removed. Brought forward because dogfooding real family documents (`docs/BUILD_PLAN.md` Phase 2) was about to happen before the originally-planned "swap right before production" point — this entry's own revisit trigger (c) explicitly requires the swap before that, so the dev-tier half of the swap could not wait. The production-tier decision (Anthropic vs. `gpt-5-mini`) remains open, still gated on a live eval run, and still deferred to just before production per the founder's explicit call (2026-09-08) — **needs `OPENAI_API_KEY` provisioned locally and in Vercel before this actually runs.**

## D-011 — Timeline event-date fallback timezone: Asia/Kolkata

`documents_timeline_idx` orders by `coalesce(document_date, (captured_at at time zone 'Asia/Kolkata')::date)`. A bare `::date` cast is not IMMUTABLE (rejected in index expressions), so a timezone must be baked in. UTC would date evening captures (18:30–24:00 IST — prime after-clinic hours) as the previous day. V1 is India-first; the index expression and every query computing event date must match exactly. **Revisit trigger:** internationalization (requires index rebuild).

## D-012 — Explanation output shape: atomic, agent-consumable cited facts (not prose)

**Context:** the organize step produces the explain-never-advise output stored in `document_explanations`. The design question is *where the facts live* — inside the human-readable `what_it_says` prose, or in structured per-item fields. Prompted by "The Future of SaaS is Agentic" (akashyap.ai): the piece's one genuinely applicable idea for a consumer health vault is that the retrieval hero-moment should feel like the software assembling the answer, not a user operating a search box while a doctor waits — a bounded retrieval agent, already parked in V1.5 behind the north-star trigger. Its V1 footprint is a schema-shape decision made now, cheap now and expensive to retrofit.

| Option | For | Against |
|---|---|---|
| **Atomic cited facts (chosen)** | A V1.5 retrieval agent assembles "what meds is X on?" by pulling `medications_as_written` items across documents + joining `documents.document_date` — no re-parse, no re-inference, no fresh model call re-opening the fabrication risk closed at capture; `what_it_says` becomes a pure human summary that adds no fact absent from the structured fields | Slightly stricter prompt (every fact must land in a typed field, not just the prose) |
| Prose blob (`what_it_says` holds the facts) | One free-text field, simplest prompt | Facts trapped in a sentence; later extraction means fragile string-parsing or a fresh AI call — the exact re-inference the pipeline exists to avoid |

**Choice:** the structured arrays are the machine truth; `what_it_says` is a human summary only. **Footprint:** shape discipline within existing columns — **no new tables/columns.** `terms`/`medications_as_written`/`tests_as_written` stay jsonb; their item shapes are enforced in `OrganizeSchema` (Zod) + typed in `lib/types/domain.ts` (Rule 10). No agent is built in V1; this only keeps the V1.5 option open for free without widening V1 scope (Rule 15).

Item shapes (verbatim-or-null on every sub-field — absent on the document = `null`, never inferred):
- `Term { term, plain_explanation }` — defines the term generically; never interprets the patient's specific value.
- `Medication { name, strength|null, frequency|null, form|null }`.
- `LabTest { name, value|null, unit|null, reference_range|null, flag_as_written|null }`.

**Why these are free strings, not enums (evaluated and rejected):** narrowing clinical fields (`frequency`, `unit`, `form`, `flag_as_written`, …) to controlled vocabularies was considered for consistency. Rejected — it collides with verbatim-or-null: an enum forces the model to either normalize what the document says ("1-0-1" or "twice a day" → `BD`), which is a Rule-2 violation and a fabrication risk in a medical record, or drop non-matching values, which loses data that was on the document (capture is sacred). The document's exact text *is* the clinical content; a doctor needs "Metformin 500mg BD as written," not our interpretation. This mirrors FHIR, which always preserves original `text` even when a code exists. Consistency is instead enforced in the **prompt**: copy these fields **character-for-character as printed** — no case-fixing, no expanding abbreviations, no re-spacing. Any inconsistency is then the document's, faithfully preserved, not the model's invention. Coded companion fields (e.g. `form_code`) beside the verbatim ones are a V1.5+ option, decided from eval evidence (does free-text inconsistency actually hurt retrieval?), never a replacement. Global terminologies (LOINC/UCUM/RxNorm/SNOMED) ride with ABDM — out of V1 (Rule 15).

**`flag_as_written` (the explain-never-advise boundary call, founder-decided):** a printed abnormality marker ("HIGH" / "H" / "↑") *is captured verbatim* — verbatim-or-null permits copying what the document says, and refusing to show what the document itself prints is dishonest to the source. The advisory line is the system *generating* a severity judgment or computing in/out-of-range — which it never does. The UI renders `flag_as_written` visually neutral, labeled "as printed on the document." `reference_range` follows the same rule: copied as printed, never compared against the value. **Revisit trigger:** an eval case where a captured printed flag reads as the app's own assessment despite neutral rendering → reconsider dropping flags entirely.

## D-013 — Eval harness runs TypeScript standalone via native type-stripping, no bundler — **RESOLVED 2026-09-07**

**Context:** `docs/PRACTICES.md` §6's eval harness (`eval/run.mjs`, `lib/eval/`) needs to run the real pipeline modules (`lib/ai/organize.ts`, `lib/validation/schemas.ts`) as a standalone script outside Next.js — CI runs it with no bundler and no dev server. Two obstacles: this repo's TypeScript files use the `@/*` path alias, which only Next's/tsconfig's resolver understands, not plain Node; and `server-only` (a marker package Next's bundler makes throw on browser import) needed to be a safe no-op here.

| Option | For | Against |
|---|---|---|
| **Native Node type-stripping + a small `module.registerHooks` resolver (chosen)** | Zero new dependencies (Hard Rule 14's dependency half stays clean); Node ≥22.18/24 support this natively; the resolver is ~30 lines, narrowly scoped to exactly `@/*` and the literal string `server-only` | Hard floor of Node ≥22.18 for anyone running `pnpm eval*` locally or in CI — `eval/loader.mjs` checks the version and exits with a clear message rather than a cryptic syntax error if it's older |
| `tsx` / `ts-node` | Battle-tested, handles path aliases and edge cases out of the box | A new runtime dependency for a small internal script — an architectural addition needing its own justification for something this repo already has a dependency-free path to |
| A build step (compile `eval/` + `lib/eval/` to JS before running) | No runtime resolver needed | Adds a build step to a script that's supposed to be a lightweight CI gate; another thing to keep in sync with source |
| Bundle the eval harness with the app's own Next.js build | Reuses existing tooling | The harness needs to run detached from a Next.js app instance in plain CI; forcing it through a full Next build for a 3-file script is disproportionate |

**Choice:** native type-stripping + the resolver in `eval/loader.mjs`, registered via `node --import ./eval/loader.mjs`. **Why:** this is genuinely a dependency-free path that a newer Node version already makes available, and the resolver is narrow enough (two intercepted specifiers, everything else falls through to Node's own resolution untouched) to audit at a glance — confirmed in a security audit of the eval harness (2026-09-07) to carry no meaningful path-traversal risk (the only source of `@/*` specifiers is this repo's own `import` statements). **Revisit trigger:** if the eval harness's scope grows enough that hand-rolling more Node-native plumbing stops being cheaper than `tsx`, or if CI/dev machines can't be kept on Node ≥22.18.

## D-014 — Eval boundary-check grounding: Indian regulatory basis — **RESOLVED 2026-09-07**

> This entry is the research record — what was found, verified, and ruled out, and why. The live, current-state checklist derived from it (rule → enforcement location → status), plus ready-to-use user-facing trust copy, lives separately in **`docs/INDIA_COMPLIANCE.md`** — that file is what to read for "what do we do today," this one is "why." Update this entry first on any new finding, then that file's checklist, in the same commit.

**Context:** the eval harness's `ADVISORY_PATTERNS` list (`lib/eval/score.ts`, D-013's harness) was built entirely from the team's own judgment about what "advisory language" looks like — no external source, no citation, nothing stopping it from drifting into either under-coverage or padded-out rules that sound safety-conscious but check nothing real. Founder request: research what actual Indian regulatory/authority bodies require for AI systems touching health documents, and ground the eval strictly in what's actually backed — explicitly rejecting anything that "sounds right" without a real source. This entry is the single place that research and its conclusions live; every other file (`CLAUDE.md`, `docs/PRACTICES.md`, `docs/INDIA_COMPLIANCE.md`, `eval/cases/README.md`, `lib/eval/score.ts`) points here rather than restating it.

**What was researched, verified against primary sources (not memory/training data):**

| Source | Status | What it actually says |
|---|---|---|
| **CDSCO, Guidance Document on Medical Device Software** (Doc No. CDSCO/MD/GD/MDSW/01/2026, final) | Official guidance interpreting binding law (Medical Devices Rules 2017) | §5.2 excludes "transfer, storage, archive data... simple search" and HIS/CIS software for "scheduling patient appointments/visits" / "store and transfer patient information" from medical-device classification — describes CareAlign's core feature set almost verbatim. But: "any additional functions that allow its use for any medical purposes... may be considered a medical device." Its "Inform clinical management" category names the exact tripwire: software that will "inform of options for treating, diagnosing, preventing, or mitigating a disease or condition." **This is the load-bearing finding: Hard Rule 1 is not just an ethics stance — it is the mechanism keeping CareAlign outside SaMD licensing.** |
| **Digital Personal Data Protection Act, 2023, s.8(3)** | Binding law (verified against the Gazette text) | A data fiduciary "shall ensure completeness, accuracy and consistency" of personal data likely to be "used to make a decision that affects" the person or "disclosed to another data fiduciary." Direct statutory backing for Hard Rule 2 and for treating a wrong asserted value as a worse failure than an honest null. Substantive DPDP obligations phase in **2027-05-14** — the real compliance date to track. |
| **DPDP Act s.9 + DPDP Rules 2025, Rule 10** | Binding law | Verifiable parental consent required before processing a child's personal data; the Fourth Schedule healthcare exemption applies to clinical establishments, not consumer apps — CareAlign is not exempt. **Product decision, not an eval-code item** — noted here so it isn't lost; needs its own review before profile-creation UI hardens further. |
| **ICMR, Ethical Guidelines for AI in Biomedical Research and Healthcare, 2023** | Official non-binding guideline | Human-in-the-loop as the central safety claim; transparency about "intention, outcome and limitation"; validation must assess "risks to... recipients of healthcare," not just accuracy. Framed around clinical-decision-support with a physician in the loop — does **not** directly validate an advise-vs-inform boundary the way CDSCO does. The one concrete, cheap idea worth banking: `needs_review` behaviour is itself a testable safety dimension (§2.2(vi))— not implemented in this pass, listed under Deferred below. |
| **Telemedicine Practice Guidelines, 2020, §5.4** | Binding — scoped to RMP-network platforms, does not bind CareAlign | Names "counsel" (not just prescribe/diagnose) as the prohibited AI act — useful vocabulary check on pattern coverage, not a new obligation. |
| **MeitY, India AI Governance Guidelines, Nov 2025** | Official, explicitly voluntary | Process-level (transparency reports, a grievance/harm-reporting mechanism). Not output-testable. One cheap idea: the existing `needs_review` manual-fix affordance could double as a "report a wrong/unsafe explanation" path feeding new eval cases — **not implemented in this pass**, listed under Deferred below. |

**Explicitly ruled out — checked, no real backing found (recorded so nobody re-adds these from a half-remembered blog post):**
- **DPDP Act does NOT give health data a sensitive/special category.** Verified directly against the Gazette text — the word "sensitive" does not appear in that context. This is a common but incorrect claim (carried over from the withdrawn 2019 bill and the old IT Act SPDI Rules) repeated by several law-firm blogs. Health data is ordinary personal data under DPDP.
- NITI Aayog's Responsible AI papers — real, but aspirational only; no concrete, checkable content for a health-AI eval.
- No ABDM AI-specific guidance found for apps outside the ABDM ecosystem (moot regardless — Hard Rule 15 already excludes ABDM integration).
- No Indian standard exists specifically for AI-generated health summaries or patient-facing health-AI transparency (searched directly).
- An "ICMR AI Rules 2026" claim from one low-quality site — uncorroborated by ICMR or any credible source, discarded.

**Choice — implemented this pass:**
1. **Six new `ADVISORY_PATTERNS` entries** (`treatment-options`, `options-for-treating`, `is-treated-with`, `can-be-treated`, `dosing-instruction`, `dosing-change`) closing the CDSCO-named gap: impersonal treatment/dosing prose with no "you" and no severity word, which passed every prior pattern untouched. Found and fixed one real false positive during implementation: `dosing-instruction` as first written also matched the prompt's own sanctioned frequency-abbreviation definitions (e.g. explaining "OD" as "taken one time each day" — required by the system prompt's own worked example, not new instruction). Narrowed to require a dosage form/route noun (tablet, ml, mg, …), which separates a fresh un-printed instruction from a jargon definition. See the comment at that pattern in `lib/eval/score.ts` for the full reasoning.
2. **Fabrication-vs-omission split in field accuracy** (`CheckKind`, `lib/eval/score.ts`): a wrong non-null value now scores and reports separately from an honest null, per DPDP s.8(3)'s accuracy duty. Surfaced in the CI table (`[N fabricated]`) and asserted by the scorer self-check in both directions.

**Deferred, not implemented this pass — named so they aren't silently lost:**
- Scoring the **visit brief** as a distinct eval surface (the DPDP s.8(3) "disclosed to another data fiduciary" trigger most plausibly attaches to it). **Not built**, because the visit brief doesn't exist yet — it's Phase 4 (`docs/BUILD_PLAN.md`), a pure read-time aggregation of fields the organize eval already scores, with no AI generation of its own. Building a mock scoring path for an unbuilt feature would be exactly the "ungrounded scaffolding" this research was meant to prevent. **Revisit trigger: before the visit brief ships, and immediately if its implementation ever adds its own AI-generated prose/summary (not just aggregation of already-scored fields) — that call needs its own eval case before shipping, not after.**
- `needs_review` outcome as a scored eval dimension (ICMR §2.2(vi)) — a real, cheap idea, but a separate scoring axis, not folded into this pass to keep the diff reviewable. **Revisit trigger:** next eval-harness extension.
- A "report a wrong/unsafe explanation" path on `needs_review` documents feeding new eval cases (MeitY grievance-mechanism ask) — a product feature, not an eval-code change. **Revisit trigger:** alongside the retry/manual-fix UI's next iteration.

## D-015 — Keepalive cron to stop Upstash's free-tier auto-deletion — **RESOLVED 2026-09-08**

> This entry is the decision record — context, options, why. The portable step-by-step pattern (route code, `vercel.json`, the proxy-exclusion gotcha, the healthchecks.io setup, everything to reuse this in another project) lives in **`docs/PLAYBOOK_FREE_TIER_KEEPALIVE_MONITORING.md`** — written to be copied elsewhere, not restated here.

**Context:** the upload rate limiter's fail-open fix (2026-09-07, `app/api/uploads/sign/route.ts`, ANTI_PATTERNS #13) went live and, when stress-tested in production the next day, showed every single rate-limit check silently failing open — `error: 'fetch failed'` reaching Upstash. Root cause: Upstash's free-tier plan deletes a database after 14 days with **no REST API traffic**, and this project's Redis had gone idle long enough to be deleted. This had been invisible before the fail-open fix because rate limiting was previously hard-disabled in code (see ANTI_PATTERNS #13's original bypass) — the fix didn't cause the outage, it's what made a pre-existing, silent infra gap observable. A new free database was created and its credentials rotated into Vercel; the recurring risk (any 14-day idle stretch re-triggers deletion) still needed a fix, not just a one-time recovery.

| Option | For | Against |
|---|---|---|
| **Scheduled keepalive ping via Vercel Cron (chosen)** | Zero new paid infra; a Vercel Cron job hitting a small authenticated route (`app/api/cron/keepalive`) is enough REST traffic to keep Upstash counting the database as active; Hobby-plan cron limits (≤1 run/day per job) are not a constraint since this needs to run far less than daily | Adds a new route + a new secret (`CRON_SECRET`) to manage; the schedule itself needs to be comfortably inside the 14-day window with margin for a missed run |
| Upgrade to Upstash's paid tier | Removes the auto-deletion behavior entirely, no code needed | Recurring cost for a database that, as of this decision, is used for nothing but a soft abuse-prevention counter — disproportionate for the current stage |
| Manually recreate the database whenever this happens again | No code changes | Exactly the failure this decision exists to stop — it already cost a debugging session to trace "fetch failed" back to a deleted free-tier database instead of a code bug |
| Switch the upload rate limiter off Upstash entirely (e.g. in-memory or Postgres-backed) | No third-party dependency to go idle | A real architectural change to a rule that's working correctly (Hard Rule 3's fail-open/fail-closed split) just to route around one free-tier's idle policy — disproportionate, and Postgres-backed rate limiting has its own tradeoffs not evaluated here |

**Choice:** `app/api/cron/keepalive` (GET, `Authorization: Bearer $CRON_SECRET` checked against the `CRON_SECRET` env var that Vercel auto-injects into cron-triggered requests) does one `redis.set()` against the same Upstash instance `lib/ratelimit.ts` already uses (exported as `redisClient`, no second client). `vercel.json` schedules it for `0 0 * * 0,3` — Sunday and Wednesday, UTC — a day-of-week schedule rather than `*/2` on the day-of-month field, which drifts unpredictably across month boundaries (a `*/2`-day schedule can produce a 1-day gap at some month ends and isn't meaningfully simpler to reason about). Sunday/Wednesday gives a worst-case 4-day gap between pings, comfortably inside the 14-day deletion window even if one run is missed. **Revisit trigger:** if Upstash changes its free-tier idle policy; if this database ever holds anything besides the rate-limit counter (recreating it would then have real data-loss stakes, not just "the counter resets"); if the project moves to a paid Upstash tier, at which point this cron can be deleted.

**Addendum — alerting on failure (2026-09-08):** a scheduled job that fails silently is only half a fix; verified via `vercel alerts rules add` that Vercel's own Alerts product (custom threshold/anomaly rules on request metrics) requires a **Pro** plan — this project, and every other project under the same Hobby-tier team, is blocked from it entirely, not just rate-limited. Rather than upgrade the whole team's plan for one low-stakes counter, `app/api/cron/keepalive` pings a free healthchecks.io dead-man's-switch (`HEALTHCHECKS_PING_URL` env var, optional — the keepalive still runs without it, just without alerting): success pings the plain URL, an Upstash-write failure pings `/fail` immediately rather than waiting for a missed schedule to be noticed. This pattern is plan-tier-independent and reusable verbatim across any other Hobby-plan project with a similar low-frequency background job.

## D-016 — Real eval documents never committed to this public repo — **RESOLVED 2026-09-08**

**Context:** `eval/cases/README.md` flagged an open risk since the eval harness landed (D-013): the 10–15 real, user-supplied, anonymised family documents that are supposed to replace the synthetic placeholders (`docs/PRACTICES.md` §6, `docs/BUILD_PLAN.md` Phase 2) would, per the harness's own original design, be committed directly to `eval/cases/` — but `care-align` is a public GitHub repository (confirmed via `gh repo view`). A single missed redaction in a real medical document (a UHID in a header, a phone number in a footer, an unredacted MRN in a PDF's text layer) becomes permanent public data the moment it's committed — `git rm` doesn't remove it from history, and forks/caches make a history rewrite unreliable as a cleanup path besides. `docs/INDIA_COMPLIANCE.md` item 6 tracked this as OPEN pending a decision.

| Option | For | Against |
|---|---|---|
| **Gitignore real case directories, keep the repo public (chosen)** | Zero new infrastructure or cost; real documents never touch git history at all — not even briefly; matches the existing `eval/results/` pattern; the repo's public status (whatever reasons it's public for) is untouched | Real fixtures aren't versioned or automatically shareable — they live only on whichever machine(s) actually run the live eval, with no built-in sync mechanism to a second contributor |
| Make the whole repository private | Simplest mental model; nothing else in the eval harness changes | Solves a narrow problem (one folder's contents) by flipping visibility for the *entire* codebase — a much bigger decision than the actual risk, with its own consequences (portfolio/open-source visibility) that have nothing to do with eval fixtures |
| A separate private fixtures repo | Real docs stay versioned and become shareable across a future team without touching the main repo's visibility | Real overhead (a second repo to create, clone, and keep in sync) for a solo-founder Phase 2 stage with no team yet to share it with — exactly the kind of premature infrastructure this project's own practices (CLAUDE.md: don't design for hypothetical future requirements) argue against building now |

**Choice:** real case directories follow a `real-*` naming convention (parallel to the existing `synthetic-*` placeholders), and `.gitignore` excludes `eval/cases/real-*/` outright. This means any future real case is excluded automatically by naming convention alone — no per-case gitignore entry to remember, no risk of a forgotten `git add -f`. Synthetic placeholders are unaffected and stay tracked exactly as before. CI continues running only `pnpm eval:smoke` against the cached synthetic cases; the live, real-document eval (`pnpm eval -- --record`) runs locally only, on whichever machine has the real fixtures. **Revisit trigger:** a second contributor ever needs to run the real eval and has no reasonable way to get the documents outside this repo (at which point a private-repo or shared-secrets-manager approach becomes worth the overhead it wasn't worth today); or the whole repo is made private for unrelated reasons, which would moot this entry's narrower scope.

## D-017 — Rule 15 clarified: showing medications vs. tracking them — **RESOLVED 2026-09-08**

> The external market/competitive research this decision draws on is kept private (`docs/private/`, gitignored) — this repo is public, and that research names specific competitors' weaknesses and this product's intended differentiation, which isn't appropriate to publish. This entry states the decision and its product-logic reasoning in full; it deliberately omits the competitive detail.

**Context:** V1 scope was reconsidered after external research into adjacent opportunities in family health management, including whether to widen into medication-intake and food tracking. The reconsideration concluded scope should stay narrow — medication and food tracking remain fully out of V1, no change there. Separately, though, the research surfaced a real ambiguity in Hard Rule 15's original wording worth fixing regardless of the wider question: it banned "medication tracking/reminders-for-doses" without saying whether *displaying* a medication list already extracted from a captured prescription counts as "tracking." Left ambiguous, that reads as a predictable scope-creep vector later.

**The one place the instinct was right:** a prescription document CareAlign already parses *is* a medication list. Refusing to ever show it on the visit brief — the moment the product exists for — would be Rule 2 in reverse: hiding what a document already says.

**Choice:** Hard Rule 15 now names the actual boundary explicitly — tracking means dose logs, intake events, adherence streaks, and reminders (new user input the product didn't already extract, or a notification obligation the product now owns); it does **not** mean rendering a current-medications list built entirely from fields already extracted from the most recent prescription, with no new input and no reminder logic. This is the same verbatim-or-null contract every other extracted field already follows — nothing new is built, no new eval surface, no new regulatory exposure (CDSCO's line is about *informing of treatment options*, not about displaying what a document says). Food and dose-intake tracking remain fully out of V1, without the same carve-out — there is no equivalent "we already extracted this" argument for either. **Revisit trigger:** any future feature that would require *new* user input about medication (a dose taken, a reminder acknowledged) — that is tracking under this rule's plain meaning and needs its own decision record, not a quiet extension of this one.

## D-018 — MVP cost ceiling: free or near-free to run and to use — **RESOLVED 2026-09-08**

**Context:** the founder set an explicit product constraint: launch an MVP that costs nothing (or under $5/month total) for both the founder to operate and for early users to use, deliberately preferring free-to-use over monetized at this stage — the goal is real usage and feedback from real families first, monetization decisions come after, not before. This is a real constraint on every infra and AI choice from here on, not a vague aspiration, so it's recorded as a decision rather than left implicit.

**What this actually costs today, checked line by line:** Vercel Hobby (free) — CI, hosting, cron (used by D-015's keepalive). Supabase free tier — Postgres + Auth + Storage, ample for a dogfood scale of one family. Upstash Redis free tier (D-015) — the upload rate limiter, now protected from idle-deletion by the keepalive cron. healthchecks.io free tier (D-015's addendum) — monitoring. PostHog free tier — analytics, already well under its event cap at this scale. Resend free tier (100 emails/day) — appointment reminders, Phase 4, not yet built but already scoped to fit. The one real, unavoidable variable cost is the AI provider: D-004 requires moving off the free OpenRouter dev-tier model to a schema-enforcing provider (Anthropic) before real scoring or launch, and that has a real per-token price.

**Is the AI cost actually a problem at MVP scale? No — checked against real rates, not assumed. Correction below reflects the actual per-model math done for D-004's revisit (2026-09-08), not the earlier back-of-envelope estimate.** This schema is output-token-heavy (atomic terms/medications/tests, not just a short classification), so the real numbers at 100 documents/month are: Claude Sonnet 5 **$4.20** (not "fractions of a dollar" as first estimated here — 84% of the $5 ceiling on its own), Claude Haiku 4.5 **$2.10**, OpenAI `gpt-5-mini` **$0.75**, OpenAI `gpt-5-nano` **$0.15** — all four genuinely enforce the extraction schema (verified provider-by-provider, not assumed; see D-004). `docs/BUILD_PLAN.md`'s own MVP definition of done is one family's documents (tens, not hundreds) organized once each plus normal incremental capture, so even Sonnet fits under the ceiling with margin — but Haiku or a cheap OpenAI model leaves far more room. **The cost ceiling is not a reason to stay on the free dev-tier model regardless of which paid model is picked** — D-004's hard gate (schema-enforcing model before real eval scoring) and this cost ceiling both point the same direction and neither blocks the other.

**Choice:** stay on free tiers for every piece of infrastructure for as long as they hold (each already has its own decision record where relevant — D-003 storage, D-004 model tier, D-015 keepalive/monitoring, D-016 eval-fixture privacy); move `AI_MODEL_TIER` off the free dev-tier model now that a genuinely cheap, schema-enforcing option exists (D-004's revisit) — dev/prod tier choice stays D-004's call, not this entry's; keep the product itself free for users through the MVP/dogfood phase — no paywall, no usage cap presented to a family member, since the stated goal is maximizing real feedback, not revenue, at this stage. **Revisit trigger:** any single free-tier limit is actually approached (Supabase row/storage caps, PostHog event cap, Resend's 100/day, Vercel Hobby's function/bandwidth limits) — cross that bridge with real usage data in hand, not preemptively; or once there's a real signal from Phase 6 dogfooding that monetization should be considered, which is a separate, later decision this entry deliberately does not make.

## D-019 — Appointments: manual entry cut, extraction-from-documents is the real shape — **RESOLVED 2026-09-09**

**Context:** `docs/BUILD_PLAN.md` Phase 3 item 1 names "keyset-paginated union (documents ∪ appointments)" as a build target, and the phase table names "reminders" as a Phase 4 deliverable. Read literally, this was executed as a manual `AppointmentForm` (title, doctor, facility, date/time) writing to the existing `appointments` table, with the timeline querying both tables and merging by event date. It was built, unit-tested, Storybook-tested, and verified live in a real browser end to end before being cut in the same session, on direct challenge: does a manual-entry form actually help the family, or was this built because a doc named the word "appointments" without checking the concrete shape against user value first?

**The actual problem:** a family already has an upcoming appointment somewhere — a phone calendar, a clinic's own WhatsApp/SMS reminder, a slip of paper the doctor handed them. A manual-entry form asks them to *retype* it into a third place, with no reminder-sending payoff yet to justify the new habit (`appointments.reminder_sent_at` is a placeholder column; nothing sends anything). This is exactly what this project's own `docs/DESIGN_REVIEW_LENS.md` already names as a failure mode: *"Old habits beat better products... every flow must be nearer to the habit than the habit is to itself."* Document capture passes that test — it redirects the existing "photograph and WhatsApp it" habit into the app. Manual appointment entry does not redirect any existing habit; it competes with a calendar app that already does the job better.

**The more likely real shape of this feature:** the natural source of "next appointment" is often already sitting in a captured document — a doctor's note saying "follow up in 3 months," a discharge summary with a follow-up date. That's extractable by the same `organize()` pipeline that already reads dates and doctor names off documents, verbatim-or-null, with zero new user habit required. This is a fundamentally different feature (an extraction schema addition, not a form) and has not been designed yet.

**Choice:** deleted the manual-entry path in full — `actions/appointments.ts`, `lib/dal/appointments.ts`, `AppointmentForm`/`AppointmentCard` and their stories, the `CreateAppointmentSchema`. Reverted the `appointments.event_date` generated column added alongside it (no consumer left to justify it — see `supabase/migrations/20260908000002_event_date_columns.sql`'s final form). Kept `documents.event_date` and the keyset-paginated timeline (`lib/dal/timeline.ts`), simplified to documents-only — that infrastructure is real and independently justified by the timeline itself, not by appointments. The `appointments` table schema is untouched and still exists (nothing currently writes to it). **Revisit trigger:** before Phase 4's "reminders" line is picked up, design appointments as document-extraction first; only build a manual add-appointment affordance as an explicit, secondary fallback for the rare appointment with no source document — never as the primary path.
